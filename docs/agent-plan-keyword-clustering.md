# Agent Plan: Keyword Clustering → Content Plan Agent

Applying the **AGENT framework** from Ty's video *"You're Not Behind (Yet): How to Build Your First AI Agent (Full Guide)"* (https://youtu.be/Bm84BAtOfQw, transcribed via HappyScribe) to one of this toolbox's processes.

## Why this process

Ty's **Rule of R** says automate a task only when it is **R**epetitive, **R**ules-based, and returns a **R**eturn on time. Scored against the three toolbox processes:

| Process | Repetitive | Rules-based | Return on time | Verdict |
|---|---|---|---|---|
| Content Analyzer | Per-draft, ad hoc | Yes | Low — already one click | Keep as chat-style tool |
| SEO Audit | Occasional per site | Heuristic, judgment-heavy | Medium | Later candidate |
| **Keyword Clustering** | Every content-planning cycle | SERP overlap → clusters → briefs is deterministic | High — hours of manual planning per run | **Build the agent here** |

Today the clustering flow is human-driven end to end: paste keywords → click Cluster → click Generate Brief per cluster → copy results out. Ty's chat-vs-agent distinction applies directly — this is currently "a meeting"; the agent version is "an employee" that runs the whole workflow and reports back.

## A — Aim for a specific outcome

**Why (before how):** I need content plans produced without me babysitting the clustering tool, so planning time goes into writing, not tooling.

**Definition of Done (one sentence):**
> Done means: given a keyword list (CSV or topic seed), a finished content plan exists in Notion — one page per cluster with target keywords, shared-SERP evidence, volume/difficulty/intent, and a full content brief — and anything ambiguous (single-keyword clusters, low-evidence overlaps) is flagged for my review rather than guessed at.

**Reverse prompt to start the build:**
> "I want to build an AI agent that turns keyword lists into finished content plans using my seo-content-toolbox clustering engine. Ask me every question you need for full clarity, then write the plan."

## G — Give it an identity

Three plain-English files, generated by AI interview (not hand-written), stored in the repo under `agent/`:

- **`agent/SOUL.md`** — how it behaves: evidence-first (never clusters without shared-SERP proof), concise, flags instead of guessing, writes briefs in the site's editorial voice, zero SEO-fluff phrases.
- **`agent/IDENTITY.md`** — who it is: name (let it pick one), role "Content Planning Agent". **Lane:** keyword clustering and brief generation only — never publishes content, never edits site code, never spends beyond the per-run DataForSEO budget cap.
- **`agent/USER.md`** — who it works for: solo SEO consultant/builder, projects it serves, preferred brief format, priority niches, cost sensitivity (~$0.002/keyword — cap runs at a defined keyword count without approval).

## E — Equip it

**Context (the moat):**
- The existing engine is the playbook: `functions/_lib/cluster-core.js` (unit-tested clustering logic) and `functions/api/cluster.js` (DataForSEO integration). The agent calls these — it does not reinvent clustering.
- Reverse-engineer the brief style from the source (Ty's preferred method): feed it past briefs/published articles and have it write `agent/playbooks/brief-style.md` capturing structure, tone, and section conventions.
- One system-prompt file per subprocess (Ty: "sort, reply, forward" → ours): `ingest`, `cluster`, `brief`, `review`, `report`.

**Tools/logins:**
- DataForSEO credentials (already server-side in the Pages Function — agent calls `/api/cluster`, never holds the raw credentials).
- Anthropic API for brief generation (reusing the existing per-cluster brief prompt from `index.html`).
- Notion MCP for delivering the content plan; Google Drive/Dropbox for CSV ingest.

**Memory:** a run log (`agent/memory/runs/`) so repeat runs skip already-planned clusters and the agent learns from brief edits I make.

## N — Narrow the scope

One specialist per job, coordinated by a manager — no mega-agent:

- **Manager agent** — never does tasks itself; routes work, monitors subagents, reports back. ("You never do any tasks yourself… one agent, one lane.")
  - **Ingest agent** — parses CSV/seed topic, dedupes, validates keyword list, enforces the cost cap. *Model: Haiku (cheap, high-volume).* 
  - **Cluster agent** — calls `/api/cluster`, validates SERP-overlap evidence, flags weak clusters. *Model: Haiku/Sonnet.*
  - **Brief agent** — writes one brief per cluster using the style playbook. *Model: Sonnet (day-to-day writing).* 
  - **Review agent** — separate from the writer (Ty: code-writer vs code-reviewer), checks briefs against the DoD and style guide. *Model: Sonnet.*
- Building/refining the agent itself: Opus or Fable. Running it: Sonnet and below. (Ty's $150-vs-$1.50 model-tiering point.)

## T — Trust in stages

1. **Guardrails first** (in the identity files): draft-only to a staging Notion page; hard keyword-count/cost cap per run; never touches live site content.
2. **Approve everything:** first runs use the demo dataset (`loadClusterDemo` path — zero API cost), then live runs where I review every cluster and brief before it lands in Notion.
3. **Loosen the leash:** auto-deliver briefs for high-evidence clusters (≥3 shared SERP URLs); still flag low-evidence clusters and single-keyword orphans for review.
4. **Heartbeat:** weekly scheduled run — pick up new keyword CSVs from a designated Drive/Dropbox folder, run the full pipeline, deliver the plan, post a summary report. Inbox-zero equivalent: "every Monday 9 AM, the keyword backlog folder is empty and the content plan is current."

## Build order

1. Generate the three identity files via reverse-prompt interview.
2. Write the five subprocess system prompts; extract the brief prompt from `index.html` into `agent/playbooks/` so UI and agent share one source.
3. Stage-1 dry runs against demo data; iterate on briefs.
4. Wire Notion delivery + run log; live runs with full approval.
5. Add the weekly heartbeat and loosen the leash per stage 3.
